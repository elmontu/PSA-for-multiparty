# OIRA — Implementation-facing threat model

This is the operational threat model for the OIRA construction (see
`OIRA_CONSTRUCTION.md`). It is deliberately narrower than the theory
version in `THEORY_OIRA_FUNCTIONALITY.md` — this doc is what an
engineer needs to know before writing code, not what a co-author needs
for a paper.

## 1. Parties

- `N ≥ 2` **data-holding parties** (banks / institutes). Each party
  `P_i` holds a set `S_i` of ids drawn from a public universe `𝒰`
  (e.g., 128-bit hashes of company identifiers).
- `1` **aggregator** `P_0` (regulator / SP). Receives the aggregate
  output.
- Optional additional trusted party for offline preprocessing (Beaver
  triples, VOLE correlations). This document treats offline preprocessing
  as an oracle; the actual `MPSICSpreGen`/`MPSICpreGen` runs
  in-process for the reference implementation.

Total: `N + 1` online parties.

## 2. Adversary model

**Static, semi-honest.** Adversary corrupts a subset
`𝒞 ⊆ {P_0, P_1, ..., P_N}` at protocol start and follows the protocol
honestly, observing all internal state of corrupted parties.

**Non-collusion assumption:** at least one honest data-holding party
exists (`𝒞 ⊉ {P_1, ..., P_N}`) AND `P_0` is either honest or corrupted
alone (SP + all-but-one banks collusion is out of scope; see §6).

**Auxiliary information:** the adversary additionally has access to a
public database `𝒟` that maps ids to feature vectors (e.g., public
financial disclosures, credit-rating databases). The adversary may
query `𝒟` up to `q` times where `q = poly(λ)`. This is the piece that
distinguishes the OIRA threat model from the standard MPSI-CS one.

## 3. What must NOT leak

Ranked by severity:

| # | Leak | Why it matters | Guarantee |
|---|---|---|---|
| 1 | Individual per-item values `v_i(id)` | Raw financial data (loan, income, ...) | **Cryptographic** — under MPSIC/MPSICS |
| 2 | Which specific ids are in the intersection | Membership = "does bank X have customer Y" | **Cryptographic + k-anon gate** |
| 3 | Per-item aggregate `a(id)` = f(v_1(id), ..., v_N(id)) | Distinctive scores enable auxiliary-info re-identification | **Structural** — release only cell-level aggregates, never per-item |
| 4 | Which id contributed a given amount to the aggregate | Same reason as #3 | **Structural + shuffle inside MPSICS** |
| 5 | Exact `|intersection|` | Small intersections enable cardinality-based re-id | **DP-noised** to `|I| + Laplace(1/ε)` |
| 6 | Exact aggregate value | Aggregate magnitude may re-id via public totals | **DP-noised** to `A + Laplace(Δ/ε)` |

## 4. What CAN leak (accepted)

- **Protocol participation:** all N + 1 parties know a session ran and
  who was involved.
- **Approximate cardinality** (post-noise): `Ĉ = |I| + Laplace(1/ε)`. A
  regulator learning "roughly 240 companies were in the intersection"
  is acceptable per operational spec.
- **Approximate aggregate** (post-noise): `Â = Σ v + Laplace(Δ/ε)`.
- **k-anonymity failure indicator:** if `|I| < k_anon`, aggregate is
  suppressed and SP learns "cell suppressed". This binary leaks
  whether cardinality exceeded threshold, which is unavoidable under
  suppression semantics.
- **Sender-side own contribution:** each party may compute how many of
  its own items were in the intersection using its share of the
  MPSICS BitIndi vector. This is by construction of MPSICS and
  documented in `docs/DESIGN_VULN_SCORE.md`.

## 5. Assumptions

**A1. Honest offline pregen.** Beaver triples and VOLE correlations
are generated by a trusted dealer OR via honest execution of
`MPSICSpreGen` / `MPSICpreGen`. The reference implementation uses
in-process pregen. Production replaces with `MpOleTriple`-based
generation (see `docs/DESIGN_VULN_SCORE.md` session 4).

**A2. Semi-honest MPSIC and MPSICS.** The vendored `MPSICardParty` and
`MPSICardSumParty` are assumed correct against semi-honest adversaries
per Dong et al. CCS'25. Malicious upgrade would require OKVS
correction from ASIACRYPT'24 (`eprint 2024/1989`).

**A3. Public feature function `φ`.** `φ : 𝒰 → ℝ^d` is a
polynomial-time-computable function known to all parties + adversary
that returns a d-dimensional feature vector per id. In production this
is a real function like "standardized ratios from public annual
filings". For the reference implementation, we treat `φ` as a black
box and don't compute it.

**A4. Public predictor `π_pub` with correctness `ρ`.** The adversary
has a polynomial-time predictor `π_pub : ℝ^d → V` such that
`Pr[|π_pub(φ(id)) − a(id)| ≤ τ] ≥ ρ`. For financial vulnerability
scoring, `ρ` is typically 0.3 – 0.8. The OIRA construction is
designed to render this predictor useless against the released
aggregate; we don't implement `π_pub` in the reference — its role is
purely to justify why per-item output is unacceptable.

## 6. Out of scope (explicitly)

- **Malicious security.** Semi-honest only. Malicious upgrade path
  requires (i) corrected OKVS in the vendored code, (ii) NIZKs for
  input consistency, (iii) verifiable aggregation. Tracked as later
  session.
- **SP + (N − 1) banks collusion.** If all-but-one bank colludes with
  SP, they can invert MPSICS's oblivious shuffle and reconstruct
  membership. This is intrinsic to the star-topology cascade; only a
  full N-party native shuffle (Gao et al. `eprint 2024/1936`) fixes
  it. Documented.
- ~~**Multi-session adaptive queries.**~~ CLOSED by Fix C (see §7):
  persistent DP-budget accountant per (party, scope). Each party
  refuses new queries when its cumulative ε or query count exceeds
  cap. Since MPSICS requires all N parties online, one honest party
  enforcing the budget suffices to block the session. Composition
  method: basic (linear ε accumulation, conservative). Upgrade to
  Rényi-DP or advanced composition is a future refinement.
- **Timing / side channels.** Not addressed; standard MPC constant-
  time assumptions.
- **Multi-jurisdictional deployment.** Reference implementation
  targets a single trust domain.

## 7. Single-session adaptive-attack defenses (Fix A + Fix B)

Two hardenings landed since the initial threat model doc:

**Fix A — Noisy-k-anon suppression boundary.** The k-anonymity gate
now compares `k_anon` against the DP-noised `noisyCardinality`, not
the true `|I|`. Previously an adaptive SP could probe the boundary
via `S_0 = {X, 19 decoys}` with `k_anon = 20` — the release/suppress
decision was a deterministic function of true `|I|`, leaking X's
membership. Now the decision is itself ε-DP.

**Fix B — S_0 input attestation.** P_0 computes a Pedersen commitment
to `Σ hashToScalar(id)` for id ∈ S_0 BEFORE Phase 1 runs. The
commitment is published to all parties (via log or side channel).
Post-hoc, P_0 can be challenged to open (revealing the hash-sum and
opening scalar); other parties verify against the recorded commit.
Prevents P_0 from swapping S_0 between sessions to run subtractive
attacks. Does NOT alone prevent multi-session composition attacks
where P_0 commits to DIFFERENT S_0 legitimately each session — that
still needs the DP-budget accountant.

Combined, Fix A + Fix B close single-session adaptive-attack vectors.

**Fix C — DP-budget accountant.** File-backed accountant
(`MpOiraBudget.{h,cpp}`) tracks `(spent_ε, query_count)` per
`(party, scope_id)`. Before each OIRA session, each party checks +
atomically reserves budget for that scope; if the reservation would
exceed either `epsilonCap` or `queryCap`, the party refuses to
participate and `oiraAggregate` returns `released=false` with
`reason="budget_exhausted: ..."`. Enforcement is coordinatively
complete: MPSICS needs all N parties online, so one honest party
enforcing the budget aborts the session.

Composition method: basic linear (ε accumulates arithmetically),
conservative. A Rényi-DP or moments-accountant upgrade would give
tighter bounds at the cost of file-format complexity — deferred.

With A + B + C, all single-session AND multi-session adaptive-query
attacks (that stay within the honest-party enforcement model) are
closed. Remaining open items:

- SP + (N − 1) banks collusion (intrinsic to star topology).
- Malicious-secure crypto (semi-honest only).
- Rényi/advanced composition tightness.

## 7. Concrete parameter defaults

| Parameter | Symbol | Default | Where it comes from |
|---|---|---|---|
| Cardinality threshold | `k_anon` | 20 | MAS TRM Guidelines k-anonymity practice; overridable |
| DP privacy budget | `ε` | 1.0 | Moderate per PoPETs conventions |
| Value bound (sensitivity) | `Δ` | max value in universe (implementation-specific) | Caller-specified upper bound on per-item value |
| Aux budget assumed | `q` | 10^6 | Adversary can afford ~1M database queries |
| Feature-informativeness | `ρ` | assumed 0.5 | Financial-domain empirical |

These defaults produce membership-inference advantage bound
(informal): `Adv ≤ ε·q · 10^{-6} + 2^{-40} + ρ/k_anon` = `~0.03`
under the defaults. Acceptable for regulator use case (< 5%
re-identification probability). Tighten by increasing `k_anon` or
decreasing `ε`.

## 8. What the reference implementation MUST NOT do

- Release per-item output at any granularity finer than one aggregate
  per session (or one per bucket cell for BOIRA).
- Bypass the k-anonymity gate.
- Skip DP noise on either cardinality or aggregate.
- Reveal internal MPSICS intermediate values to SP outside the
  protocol-defined output.
- Log raw ids or values in a way that survives the protocol run.

## 9. What the reference implementation IS permitted to do

- Compute the aggregate in the clear inside the SP's process AFTER
  MPSICS completes, then apply DP noise. (The MPSICS protocol
  guarantees SP-side plaintext exposure is limited to the aggregate
  scalar.)
- Log cardinality-check outcomes (`passed` / `suppressed`) — the
  binary leak is accepted per §4.
- Cache pregen artifacts across sessions if `ε` is amortized
  correctly (not for the first implementation — one session, fresh
  pregen).
